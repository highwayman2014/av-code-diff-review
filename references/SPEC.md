# Контракт спецификации

Спецификация содержит пояснения. Код сборщик читает из двух ревизий Git.

## Поля верхнего уровня

| Поле | Требование | Значение |
|---|---|---|
| `task` | Обязательно | Название отчета или ключ задачи. |
| `repo` | Обязательно | Локальный Git-репозиторий. Относительный путь считается от каталога JSON. |
| `base`, `head` | Задавай оба поля | Полные SHA начала и конца сравнения. |
| `methods` | Обязательно | Непустой список методов в порядке чтения. |
| `file` | Если у метода нет своего `file` | Путь модуля от корня репозитория. |
| `main` | Необязательно | Ветка для вычисления базы без `base`. По умолчанию `main`. |
| `out` | Не задавай при работе через обертку | Обертка определяет результат через `--out`. |

Runtime допускает отсутствие `base` и `head`. Для воспроизводимого отчета сохраняй оба SHA.
Рабочие изменения вне коммитов в отчет не входят.

## Поля метода

| Поле | Требование | Значение |
|---|---|---|
| `id` | Обязательно | Уникальный якорь: латинская буква, затем строчные латинские буквы, цифры или дефисы. |
| `method` | Обязательно | Точное имя процедуры или функции BSL. |
| `lead` | Обязательно | Тезис одной фразой, до 70 символов. |
| `hunks` | Обязательно | Непустой список смысловых фрагментов. |
| `file` | Необязательно | Путь модуля вместо общего `file`. |
| `collapse` | Необязательно | Диапазоны строк для сворачивания: `[[с, по], …]`. |

Включай только измененные, добавленные или удаленные методы.
Сборщик ищет объявления с начала строки: `Функция Имя(` или `Процедура Имя(`.
Текущий поиск учитывает регистр и не поддерживает все варианты синтаксиса BSL.
Изменения вне методов этот формат не описывает.

## Поля фрагмента

- `at` — номер строки нового кода. Для удаленного метода это номер строки старого кода.
- `blocks` — список абзацев и дополнительных блоков.

Задавай уникальные `at` по возрастанию.
Фрагмент продолжается до следующего `at`.
Строки до первого `at` входят в первый фрагмент.
После смены SHA проверь все номера строк.

Строка в `blocks` задает абзац.
Объект задает дополнительный блок:

| `type` | Поля | Назначение |
|---|---|---|
| `flow` | `steps`: список строк | Последовательность шагов. Запись `*шаг*` выделяет шаг. |
| `pseudo` | `text`: строка | Псевдокод. |
| `diagram` | `edges`: пары строк; `mark`: объект | Схема. Значения `mark`: `new` или `old`. |
| `table` | `head`: список строк; `rows`: список строк таблицы | Правила «условие → результат». |

Общее поле `label` заменяет подпись блока.
Поле `place` задает положение:

- `summary` — после тезиса, перед фрагментами.
- `before` — после пояснения фрагмента, перед кодом.
- Поле отсутствует — после кода фрагмента.

В `summary` используй не больше одного блока каждого типа.
Выбор вида и правила схем описаны в [visual-explanations.md](visual-explanations.md).

## Содержание

- Разделяй код при смене смысла, а не при каждой группе строк Git.
- Для простого изменения используй один фрагмент.
- Для длинного добавленного метода обычно достаточно 2–5 фрагментов.
- Каждому фрагменту дай 1–3 абзаца.
- В абзаце используй 1–3 коротких предложения.
- Объясняй цель и изменение поведения. Не пересказывай строки кода.
- Первую фразу пиши как вывод. Сборщик выделит ее полужирным.
- Риск выделяй отдельным абзацем `Важно: …`.
- Используй один термин для одного понятия.
- Используй кавычки «елочки». Пиши обычный текст без Markdown и эмодзи.

## Сворачивание и размер

Неизмененные строки дальше трех строк от изменения сворачиваются автоматически.
Для длинного запроса или однотипного кода задай `collapse`.
Используй номера нового кода, а для удаленного метода — старого.
Размещай диапазон внутри одного фрагмента.

Сворачивание скрывает код, но оставляет его в HTML.
Оно не уменьшает байтовый размер страницы.
Лимит одной страницы — 200 000 байт.
Если отчет превышает лимит, раздели спецификацию по смыслу.
Сохрани одинаковые SHA во всех частях.
Сверь общий список методов после разделения.
